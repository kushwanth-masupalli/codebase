250 SYSTEM DESIGN INTERVIEW QUESTIONS WITH ANSWERS (FOR FRESHERS)
Based on the AlgoMaster System Design Roadmap - Fundamentals through Advanced Security
====================================================================================


=== SECTION 1: CORE CONCEPTS ===

1. Q: What is scalability and why does a system need it?
A: Scalability is a system's ability to handle increasing load (more users, requests, or data) without a drop in performance. Systems need it because traffic and data volume naturally grow over time, and a system that can't scale will slow down or crash under load, directly hurting user experience and business revenue.

2. Q: What is the difference between scaling up and scaling out?
A: Scaling up (vertical scaling) means adding more resources (CPU, RAM) to a single machine. Scaling out (horizontal scaling) means adding more machines to distribute the load. Horizontal scaling is generally preferred for large systems because it has no hard upper limit and improves fault tolerance, while vertical scaling is simpler but hits a hardware ceiling.

3. Q: What is availability and how is it measured (e.g. 99.9% uptime)?
A: Availability is the percentage of time a system is operational and able to serve requests. It's usually expressed as "nines" - e.g., 99.9% ("three nines") allows about 8.7 hours of downtime per year, while 99.99% allows only about 52 minutes per year.

4. Q: What is the difference between availability and reliability?
A: Availability measures whether the system is up and responding right now. Reliability measures whether the system performs correctly and consistently over time without failures. A system can be available but still return wrong results (unreliable), or briefly unavailable but otherwise very reliable.

5. Q: What is a Single Point of Failure (SPOF) and how do you eliminate one?
A: An SPOF is any single component whose failure brings down the entire system. You eliminate it through redundancy - running multiple instances behind a load balancer, replicating databases, and avoiding designs where one server, one database, or one network link is critical to everything.

6. Q: What is latency and how is it different from throughput and bandwidth?
A: Latency is the time it takes for a single request to get a response (e.g., 100ms). Throughput is the number of requests a system can process per unit time (e.g., 1000 requests/second). Bandwidth is the maximum data transfer capacity of a network link. A system can have low latency but low throughput, or vice versa.

7. Q: What is consistent hashing and what problem does it solve?
A: Consistent hashing maps both servers and data keys onto a hash ring, so each key is stored on the "nearest" server on the ring. It solves the problem of massive data reshuffling when servers are added or removed - with simple modulo hashing almost all keys would need to move, but with consistent hashing only a small fraction do.

8. Q: How does adding/removing a node affect data distribution in consistent hashing?
A: Only the keys that fall in the range between the new/removed node and its neighbor on the hash ring are affected - all other keys stay on their original server. This minimizes data movement compared to a full rehash, which is why it's used in distributed caches and databases.

9. Q: What is the CAP theorem and what trade-off does it describe?
A: CAP theorem states that a distributed system can only guarantee two of three properties at the same time: Consistency (all nodes see the same data), Availability (every request gets a response), and Partition Tolerance (the system keeps working despite network failures). Since network partitions are unavoidable in practice, real systems must choose between consistency and availability when a partition occurs.

10. Q: Give a real-world example of choosing Availability over Consistency (or vice versa).
A: A shopping cart service (like Amazon's) favors Availability - it's better to let a user add an item even if all replicas aren't synced yet, than to reject the request. A banking system transferring money favors Consistency - it's better to briefly reject a transaction than to risk showing an incorrect balance.

11. Q: What are the common consistency models (strong, eventual, causal)?
A: Strong consistency means every read gets the latest write immediately, guaranteeing correctness but often at the cost of latency. Eventual consistency means all replicas will converge to the same value eventually, but reads may temporarily see stale data. Causal consistency guarantees that operations which are causally related are seen in the same order by everyone, while unrelated operations can be seen in any order.

12. Q: What is the difference between fault tolerance and high availability?
A: Fault tolerance is a system's ability to keep functioning correctly even when a component fails, often with zero disruption. High availability is the broader goal of minimizing downtime, which fault tolerance is one strategy for achieving alongside redundancy, failover, and quick recovery.

13. Q: What is meant by 'five nines' (99.999%) availability and what does it imply about downtime?
A: Five nines means the system is available 99.999% of the time, which allows only about 5 minutes of downtime per year. Achieving this requires extremely redundant infrastructure, automated failover, and rigorous operational practices, and is typically reserved for mission-critical systems like telecom or payment infrastructure.

14. Q: What is redundancy and how does it improve reliability?
A: Redundancy means having duplicate components (servers, databases, network paths) so that if one fails, another can take over. It improves reliability by removing single points of failure and enabling automatic failover, so the overall system keeps working even when individual parts fail.

15. Q: Why is it said that 'everything fails at scale' and how should system design account for it?
A: At scale, even very rare failure probabilities become frequent in absolute terms - with thousands of servers, disks, and network links, something is failing at almost any given moment. Good system design assumes failure is normal, not exceptional, and builds in redundancy, retries, timeouts, and graceful degradation rather than assuming components will always work.

16. Q: What is the difference between vertical and horizontal partitioning of load across servers?
A: Vertical partitioning of load splits work by function - e.g., one set of servers handles reads, another handles writes, or different servers handle different services. Horizontal partitioning of load spreads similar work across many identical servers (e.g., via a load balancer), so each server handles a subset of the same type of traffic.

17. Q: What is meant by graceful degradation when part of a system fails?
A: Graceful degradation means that when part of a system fails, the overall system keeps working with reduced functionality instead of failing completely. For example, if a recommendation service goes down, an e-commerce site can still show products without personalized suggestions rather than showing an error page.

18. Q: What is a 'circuit breaker trip' and how does the system recover from it automatically?
A: A circuit breaker is a resilience pattern that prevents repeated calls to a failing service. When failures exceed a threshold, the circuit breaker trips and enters the Open state, where requests fail immediately instead of waiting for timeouts. After a cooldown period, it enters the Half-Open state and allows a few test requests. If they succeed, the breaker closes and normal traffic resumes; otherwise, it opens again.


=== SECTION 2: NETWORKING ===

19. Q: What is the OSI model and what are its 7 layers?
A: The OSI model is a conceptual framework describing how data travels across a network in 7 layers: Physical, Data Link, Network, Transport, Session, Presentation, and Application. Each layer has a specific responsibility, and understanding it helps engineers reason about where in the stack a networking issue or feature belongs (e.g., HTTP is Application layer, TCP is Transport layer).

20. Q: What is an IP address and what is the difference between IPv4 and IPv6?
A: An IP address is a unique numerical identifier assigned to a device on a network so it can send and receive data. IPv4 uses 32-bit addresses (about 4.3 billion possible addresses, which have run out), while IPv6 uses 128-bit addresses, providing a vastly larger address space to support the growing number of internet-connected devices.

21. Q: What is the difference between TCP and UDP, and when would you use each?
A: TCP is connection-oriented and guarantees reliable, ordered delivery of data (with acknowledgments and retransmission), making it ideal for web pages, APIs, and file transfers. UDP is connectionless and faster but doesn't guarantee delivery or order, making it suitable for real-time applications like video streaming, gaming, and voice calls where speed matters more than perfect reliability.

22. Q: What happens during a TCP three-way handshake?
A: The client sends a SYN (synchronize) packet to the server to initiate a connection. The server responds with a SYN-ACK (synchronize-acknowledge) packet. The client then sends an ACK (acknowledge) packet back, completing the handshake and establishing a reliable connection before any data is transferred.

23. Q: What is the difference between HTTP and HTTPS?
A: HTTP transmits data in plain text, making it vulnerable to eavesdropping and tampering. HTTPS adds a layer of encryption (TLS/SSL) on top of HTTP, encrypting the data in transit so it can't be read or modified by attackers, and also verifies the identity of the server via certificates.

24. Q: How does the Domain Name System (DNS) resolve a domain name to an IP address?
A:
Browser checks its DNS cache.
If not found, the operating system checks its DNS cache.
If still not found, the request goes to the recursive DNS resolver (usually provided by your ISP or a public DNS like Google or Cloudflare).
The recursive resolver checks its own cache.
If not found, the recursive resolver queries a Root DNS server.
The Root DNS server replies with the address of the appropriate Top-Level Domain (TLD) server (e.g., .com, .org, .in).
The recursive resolver queries the TLD server.
The TLD server replies with the address of the authoritative name server for the domain.
The recursive resolver queries the authoritative name server.
The authoritative name server returns the IP address.
The resolver caches the result and returns the IP to the browser.

25. Q: What is a checksum and how is it used to detect data corruption?
A: A checksum is a small value computed from a block of data using a hashing function, sent along with the data. The receiver recomputes the checksum on the received data and compares it to the sent value - if they don't match, the data was corrupted in transit and can be discarded or re-requested.

26. Q: What is the difference between a forward proxy and a reverse proxy?
A: A forward proxy sits in front of clients and forwards their requests to the internet, often used to hide client identity or enforce access policies (e.g., corporate proxies). A reverse proxy sits in front of servers and forwards client requests to the appropriate backend, commonly used for load balancing, caching, and SSL termination.

27. Q: What is the difference between HTTP/1.1, HTTP/2, and HTTP/3?
A: HTTP/1.1 processes one request per TCP connection at a time (or with limited pipelining), causing head-of-line blocking. HTTP/2 introduces multiplexing - multiple requests/responses over a single connection - along with header compression and server push. HTTP/3 replaces TCP with QUIC (built on UDP), eliminating TCP-level head-of-line blocking and improving performance on unreliable networks.

28. Q: What are common HTTP methods and what is each used for?
A: GET retrieves a resource without side effects. POST creates a new resource or triggers an action. PUT replaces a resource entirely. PATCH partially updates a resource. DELETE removes a resource. Each method also carries semantic meaning about idempotency and safety that clients and caches rely on.

29. Q: What do HTTP status code ranges (2xx, 3xx, 4xx, 5xx) generally mean?
A: 2xx means success (e.g., 200 OK, 201 Created). 3xx means redirection (e.g., 301 Moved Permanently). 4xx means a client error (e.g., 404 Not Found, 401 Unauthorized). 5xx means a server error (e.g., 500 Internal Server Error, 503 Service Unavailable).

30. Q: What is a port number and why do services need one?
A: A port number is a 16-bit number that identifies a specific process or service running on a machine (e.g., 80 for HTTP, 443 for HTTPS). Ports let a single machine with one IP address run multiple network services simultaneously, since the OS routes incoming traffic to the correct application based on the port.

31. Q: What is the difference between a public IP and a private IP address?
A: A public IP address is globally unique and routable on the internet. A private IP address (e.g., 192.168.x.x) is only valid within a local network and isn't directly reachable from the internet, which is why devices behind a router typically share one public IP via NAT.

32. Q: What is NAT (Network Address Translation) and why is it used?
A: NAT translates private IP addresses used within a local network into a single public IP address (and back) when communicating with the internet. It's used to conserve the limited pool of public IPv4 addresses and to add a layer of security by hiding internal network structure.

33. Q: What is a subnet and why are networks divided into subnets?
A: A subnet is a smaller, logically segmented portion of a larger network. Networks are divided into subnets to improve organization, reduce broadcast traffic, isolate different parts of infrastructure (e.g., public vs. private subnets in a cloud VPC), and apply different security policies to each segment.

34. Q: What is the difference between a TCP connection timeout and a read timeout?
A: A connection timeout is the maximum time a client waits while trying to establish a TCP connection with the server. A read timeout is the maximum time the client waits for data once the connection is established, e.g., waiting for the server's response body. Both need sensible limits to avoid requests hanging indefinitely.


=== SECTION 3: LOAD BALANCING ===

35. Q: What is a load balancer and why is it needed in a system?
A: A load balancer distributes incoming traffic across multiple backend servers so no single server is overwhelmed. It's needed to improve availability (traffic can be rerouted if a server fails), scalability (more servers can be added behind it), and performance (requests are spread evenly).

36. Q: What are common load balancing algorithms (round robin, least connections, weighted, etc.)?
A: Round robin sends requests to servers in rotating order. Least connections sends the next request to the server with the fewest active connections. Weighted round robin/least connections factors in server capacity so more powerful servers get more traffic. IP hash routes a client consistently to the same server based on their IP.

37. Q: What is DNS load balancing and how does it work?
A: DNS load balancing returns different IP addresses for the same domain name to different clients (often in rotation), spreading traffic across multiple servers or data centers at the DNS resolution step. It's simple to set up but has limited control over real-time server load and can be slow to react to server failures due to DNS caching.

38. Q: What is Anycast routing and how is it used for load balancing?
A: Anycast lets multiple servers in different locations share the same IP address, and network routing automatically sends each client's request to the topologically nearest one. It's used by CDNs and DNS providers to reduce latency and provide automatic failover if one location goes down.

39. Q: What is the difference between Layer 4 and Layer 7 load balancing?
A: Layer 4 load balancing operates at the transport layer, routing traffic based on IP address and port without inspecting the actual content - it's fast but less flexible. Layer 7 load balancing operates at the application layer, allowing routing decisions based on HTTP headers, URLs, or cookies, enabling smarter routing (e.g., sending /api requests to one service and /images to another).

40. Q: What is a sticky session and what problem can it cause with load balancing?
A: A sticky session (session affinity) ensures a client's requests are always routed to the same backend server, often used when session data is stored locally on that server. The problem is it undermines even load distribution and creates a soft single point of failure - if that server goes down, the user's session data can be lost.

41. Q: What is health checking in a load balancer and why is it important?
A: Health checking is the load balancer periodically pinging backend servers (via a lightweight endpoint) to verify they're up and responsive. It's important because it lets the load balancer automatically stop sending traffic to unhealthy servers, preventing users from hitting broken instances.

42. Q: What is the difference between a hardware load balancer and a software load balancer?
A: A hardware load balancer is a dedicated physical appliance optimized for high throughput and low latency, but expensive and less flexible. A software load balancer (e.g., NGINX, HAProxy, or cloud load balancers) runs as software on commodity servers, is cheaper and more flexible to configure, and is the more common choice in modern cloud-based systems.

43. Q: How would you design a load balancer to avoid becoming a single point of failure itself?
A: Run multiple load balancer instances behind a floating/virtual IP or DNS-based failover, so if one load balancer fails, traffic automatically shifts to another. Many cloud providers offer managed load balancers that are inherently redundant across multiple availability zones, removing the need to manage this manually.


=== SECTION 4: API FUNDAMENTALS ===

44. Q: What is an API and what role does it play in system design?
A: An API (Application Programming Interface) is a defined contract that lets different software components communicate with each other. In system design, APIs define how clients talk to servers and how services talk to each other, forming the connective tissue that lets independently built components work together.

45. Q: What is idempotency and why does it matter for API design?
A: An operation is idempotent if performing it multiple times has the same effect as performing it once (e.g., setting a value to X). It matters because networks are unreliable - if a client doesn't get a response and retries, idempotent operations are safe to repeat, while non-idempotent ones (like "increment balance by $10") could cause serious bugs like double charges.

46. Q: What are common data formats used in APIs (JSON, XML, Protobuf) and their trade-offs?
A: JSON is human-readable, widely supported, and the default for most REST APIs, but it's verbose and slower to parse than binary formats. XML is also human-readable and supports schemas but is even more verbose than JSON. Protobuf is a compact binary format that's much faster to serialize/parse and smaller over the wire, but it's not human-readable and requires a defined schema.

47. Q: What are the main API architectural styles (REST, GraphQL, gRPC, SOAP)?
A: REST uses standard HTTP methods and resource-based URLs, is simple and widely adopted. GraphQL lets clients request exactly the fields they need in a single query. gRPC uses Protobuf over HTTP/2 for fast, strongly-typed service-to-service communication. SOAP is an older, XML-based, heavily standardized protocol often used in enterprise/legacy systems.

48. Q: What are the key principles of good REST API design?
A: Use nouns (resources) in URLs, not verbs (e.g., /users, not /getUsers). Use HTTP methods correctly (GET, POST, PUT, DELETE). Return proper status codes. Keep endpoints stateless. Version the API. Support pagination and filtering for collections. Keep responses consistent and predictable.

49. Q: What is GraphQL and how does it solve the over-fetching/under-fetching problem in REST?
A: GraphQL is a query language that lets clients specify exactly which fields they want in a single request. In REST, a client might over-fetch (getting more data than needed from a fixed endpoint) or under-fetch (needing multiple round trips to combine data from different endpoints) - GraphQL solves both by letting the client shape the response and fetch nested/related data in one request.

50. Q: What are the main trade-offs of GraphQL compared to REST?
A: GraphQL gives clients flexibility and reduces over/under-fetching, but it's harder to cache at the HTTP level (since most requests go to a single endpoint), can allow clients to construct expensive/complex queries that strain the server, and has a steeper learning curve for building and securing the schema/resolvers.

51. Q: What is gRPC and why is it often used for internal service-to-service communication?
A: gRPC is a high-performance RPC framework that uses Protobuf for serialization and HTTP/2 for transport, supporting features like bidirectional streaming. It's popular for internal microservice communication because it's much faster and more compact than JSON/REST, and the strongly-typed contracts (via .proto files) reduce integration bugs between services.

52. Q: What is an API Gateway and what responsibilities does it typically handle?
A: An API Gateway is a single entry point that sits in front of backend services and routes client requests to the right service. It typically handles authentication, rate limiting, request routing, load balancing, logging, and sometimes response aggregation from multiple services, so individual services don't have to duplicate that logic.

53. Q: What is rate limiting and why is it important for APIs?
A: Rate limiting restricts how many requests a client can make in a given time window. It's important to prevent abuse (accidental or malicious), protect backend services from being overwhelmed, ensure fair usage across clients, and control infrastructure costs.

54. Q: What is the difference between authentication and authorization?
A: Authentication verifies who a user is (e.g., logging in with a username/password). Authorization determines what an authenticated user is allowed to do (e.g., whether they can access a specific resource or perform a specific action). Authentication always happens first.

55. Q: What is the difference between session-based and token-based authentication?
A: Session-based authentication stores session state on the server (usually in memory or a database) and gives the client a session ID via a cookie; the server looks up the session on each request. Token-based authentication (e.g., JWT) embeds the user's identity/claims directly in a signed token that the client sends with each request, so the server doesn't need to store session state, making it easier to scale across multiple servers.

56. Q: What is a JWT (JSON Web Token) and what does it contain?
A: A JWT is a compact, self-contained token used for authentication, consisting of three parts: a header (algorithm info), a payload (claims like user ID and expiration), and a signature (used to verify the token hasn't been tampered with). Because it's self-contained and signed, a server can validate it without a database lookup.

57. Q: What is OAuth 2.0 and how does the authorization flow work at a high level?
A: OAuth 2.0 is an authorization framework that lets a user grant a third-party application limited access to their resources without sharing their password. At a high level, the user authenticates with the resource owner (e.g., Google), grants permission, and the app receives an access token it can use to call APIs on the user's behalf.

58. Q: What is Single Sign-On (SSO) and how does it improve user experience across apps?
A: SSO lets a user log in once with a central identity provider and gain access to multiple related applications without logging in again for each one. It improves user experience by reducing password fatigue and login friction, and improves security by centralizing authentication and enforcement of policies like MFA.

59. Q: What is API versioning and why is it necessary as an API evolves?
A: API versioning is the practice of labeling different iterations of an API (e.g., /v1/, /v2/) so that changes don't break existing clients. It's necessary because APIs evolve over time - fields get added, removed, or restructured - and without versioning, updating the API could silently break every client depending on the old contract.

60. Q: What is pagination in an API and what are common approaches (offset vs cursor)?
A: Pagination splits large result sets into smaller pages so clients don't have to fetch everything at once. Offset-based pagination uses a page number/offset and limit (simple but can skip/duplicate items if data changes between requests). Cursor-based pagination uses a pointer to the last seen item, which is more consistent and efficient for large, frequently-changing datasets.

61. Q: What is the difference between the Token Bucket and Leaky Bucket rate limiting algorithms?
A: Token Bucket adds tokens to a bucket at a fixed rate, and each request consumes a token - this allows short bursts of traffic as long as tokens are available. Leaky Bucket processes requests at a fixed constant rate regardless of burstiness, smoothing out traffic but not allowing bursts even if capacity is technically available.

62. Q: What is the difference between authentication tokens stored in cookies vs. local storage?
A: Cookies (especially HttpOnly ones) are automatically sent with every request and are not accessible to JavaScript, making them more resistant to XSS attacks but vulnerable to CSRF if not protected. Local storage is accessible via JavaScript, making it vulnerable to XSS attacks if the site has any script injection vulnerability, though it avoids CSRF concerns since it isn't automatically attached to requests.

63. Q: What is the difference between a PUT and a POST request?
A: PUT is used to fully replace a resource at a known URL and is idempotent - sending the same PUT multiple times produces the same result. POST is used to create a new resource or trigger a non-idempotent action, and typically the server assigns the resource's identity/URL rather than the client.

64. Q: Why should GET requests be idempotent and side-effect free?
A: GET is meant to only retrieve data, not change server state, which is what makes it "safe." This matters because browsers, proxies, and crawlers can retry, cache, or prefetch GET requests freely, assuming they have no side effects - if a GET request caused a state change (like deleting data), those automated behaviors could cause serious unintended consequences.

65. Q: What is HATEOAS in REST API design?
A: HATEOAS (Hypermedia as the Engine of Application State) is a REST constraint where API responses include links to related actions/resources, so clients can navigate the API dynamically rather than hardcoding URLs. It's rarely fully implemented in practice but represents the "purest" form of REST as originally defined.

66. Q: What is the N+1 query problem and how can GraphQL both help and cause it?
A: The N+1 query problem happens when fetching a list of N items triggers one additional query per item to get related data, resulting in N+1 total queries instead of a more efficient batched query. GraphQL can help by letting clients fetch nested data in one request, but poorly written resolvers can actually cause N+1 problems on the backend if each field resolver independently queries the database.

67. Q: What is API throttling and how is it different from rate limiting?
A: Throttling and rate limiting are closely related - throttling typically refers to slowing down or queuing requests once a threshold is exceeded (rather than outright rejecting them), while rate limiting more strictly caps and rejects requests beyond a limit. In practice the terms are often used interchangeably.

68. Q: What is refresh token rotation and why is it used with JWTs?
A: Refresh token rotation issues a new refresh token every time one is used to get a new access token, invalidating the old one. It's used to limit the damage if a refresh token is stolen - since each token can only be used once, a stolen token being reused by an attacker (after the legitimate user already used theirs) can be detected and the whole session revoked.

69. Q: What is CORS and why is it needed for browser-based API calls?
A: CORS (Cross-Origin Resource Sharing) is a browser security mechanism that restricts web pages from making requests to a different domain than the one that served the page, unless the server explicitly allows it via response headers. It's needed to protect users from malicious sites silently making requests to other sites using the victim's credentials.

70. Q: What is the difference between a public API and a private/internal API?
A: A public API is exposed for external developers or partners to use, and typically needs strong versioning, documentation, and rate limiting since you don't control the callers. A private/internal API is only used within an organization's own systems (e.g., between microservices), so it can evolve more freely and often has looser authentication requirements since it's within a trusted network.


=== SECTION 5: COMMUNICATION PATTERNS ===

71. Q: What is long polling and how does it differ from regular polling?
A: In regular polling, the client repeatedly asks the server "is there new data?" at fixed intervals, even when there's nothing new. In long polling, the client sends a request and the server holds it open until new data is available (or a timeout occurs), then responds - reducing unnecessary requests compared to fixed-interval polling.

72. Q: What are WebSockets and when should you use them instead of HTTP requests?
A: WebSockets provide a persistent, full-duplex connection between client and server, allowing either side to send messages at any time without the overhead of opening a new connection each time. Use them for real-time, bidirectional communication like chat apps, live dashboards, or multiplayer games, where frequent low-latency updates in both directions are needed.

73. Q: What are Server-Sent Events (SSE) and how do they differ from WebSockets?
A: SSE allows a server to push updates to the client over a single long-lived HTTP connection, but only in one direction (server to client). WebSockets allow bidirectional communication. SSE is simpler to implement and works over standard HTTP, making it a good fit for use cases like live news feeds or notifications where the client doesn't need to send data back over the same channel.

74. Q: What is a webhook and how does it differ from a client polling an API?
A: A webhook is a callback URL that a service calls automatically when a specific event happens, pushing data to the subscriber in real time. Polling requires the client to repeatedly ask "did anything happen?", wasting resources when nothing has changed - webhooks flip this so the server notifies the client only when there's something to report.

75. Q: How would you make a webhook delivery system reliable (retries, signatures, idempotency)?
A: Use retries with exponential backoff for failed deliveries, and a dead letter queue for events that repeatedly fail. Sign each payload (e.g., with an HMAC secret) so the receiver can verify authenticity. Include a unique event ID so receivers can deduplicate and safely ignore repeated deliveries caused by retries.

76. Q: What is WebRTC and what kind of applications typically use it?
A: WebRTC is a technology that enables direct, low-latency peer-to-peer communication (audio, video, or data) between browsers/devices, often bypassing the server for the actual media stream. It's used in video calling apps, live streaming, and peer-to-peer file sharing applications.

77. Q: What is the difference between synchronous and asynchronous communication between services?
A: In synchronous communication, the caller sends a request and waits (blocks) for a response before continuing, like a typical REST API call. In asynchronous communication, the caller sends a message and continues without waiting, often via a message queue, and the response (if any) is handled later - this decouples services and improves resilience to slow downstream systems.

78. Q: What is a message queue and what problem does it solve between producer and consumer?
A: A message queue is an intermediary that stores messages sent by producers until consumers are ready to process them. It solves the problem of tight coupling and backpressure - producers don't need consumers to be available or fast in real time, which improves reliability and lets each side scale independently.

79. Q: What is the Pub/Sub pattern and how is it different from a simple message queue?
A: In Pub/Sub, publishers send messages to a topic, and any number of subscribers can receive a copy of each message. A simple queue typically delivers each message to only one consumer. Pub/Sub is used when multiple independent services need to react to the same event, while queues are used for distributing work among a pool of workers.

80. Q: What is the difference between a message queue topic and a queue in terms of consumers?
A: A queue typically has competing consumers, where each message is delivered to and processed by only one consumer, making it good for load distribution. A topic broadcasts each message to all subscribed consumers, making it good for fan-out scenarios where multiple systems need to react independently to the same event.

81. Q: What is Change Data Capture (CDC) and where is it used?
A: CDC is a technique for capturing changes (inserts, updates, deletes) made to a database in real time and streaming them to other systems. It's used to keep a cache, search index, or data warehouse in sync with the source database without the application having to explicitly publish every change itself.

82. Q: What are the different message delivery semantics (at-most-once, at-least-once, exactly-once)?
A: At-most-once means a message is delivered zero or one times - it may be lost but never duplicated. At-least-once means a message is guaranteed to be delivered but may be duplicated (requiring idempotent consumers). Exactly-once means each message is processed exactly one time, which is the hardest to guarantee and usually requires deduplication logic combined with at-least-once delivery.

83. Q: What is a Dead Letter Queue (DLQ) and why is it useful?
A: A DLQ is a separate queue where messages are sent after they fail to be processed successfully after a number of retries. It's useful because it prevents "poison messages" from blocking the main queue indefinitely, and lets engineers inspect and debug failed messages separately without losing them.

84. Q: What is Kafka commonly used for and how does it differ from RabbitMQ?
A: Kafka is a distributed event streaming platform designed for high-throughput, durable, replayable logs of events, commonly used for event sourcing, log aggregation, and real-time analytics pipelines. RabbitMQ is a traditional message broker optimized for flexible routing and lower-latency task queues, but it's not designed for the same scale or long-term message retention/replay that Kafka offers.

85. Q: How do you verify that a webhook request actually came from the expected sender?
A: The sender signs the payload with a shared secret (typically using HMAC) and includes the signature in a request header. The receiver recomputes the signature using the same secret and compares it - if they match, the request is authentic and hasn't been tampered with.

86. Q: What is fan-out messaging and where is it used (e.g. notifications)?
A: Fan-out is when a single event triggers messages to be sent to many recipients or systems at once, often via a pub/sub topic that multiple subscribers listen to. It's commonly used in notification systems (one "new post" event triggers push notifications to all followers) and in social media feed generation.

87. Q: What is backpressure and how do consumers signal it to producers?
A: Backpressure occurs when a consumer can't keep up with the rate of incoming data/requests from a producer. Consumers signal it by slowing acknowledgments, using bounded queues that block or reject once full, or explicitly requesting the producer to pause/slow down (as in reactive streams protocols).

88. Q: What is the difference between a competing consumers pattern and broadcast messaging?
A: In the competing consumers pattern, multiple consumers pull from the same queue, but each message is processed by only one of them, distributing the workload. In broadcast messaging (pub/sub), every subscriber receives a copy of each message, since the goal is for multiple independent systems to react to the same event.

89. Q: How would you ensure exactly-once processing when a consumer might crash mid-processing?
A: True exactly-once delivery is very hard to guarantee, so in practice systems combine at-least-once delivery with idempotent processing - each message carries a unique ID, and the consumer checks (often via a database) whether that ID has already been processed before applying the effect again, effectively achieving exactly-once semantics at the application level.


=== SECTION 6: CACHING ===

90. Q: What is caching and why does it improve system performance?
A: Caching is storing a copy of frequently accessed data in a faster storage layer (like memory) so future requests can be served without recomputing or refetching from the original, slower source. It improves performance by reducing latency and offloading load from databases or expensive computations.

91. Q: What is the Cache-Aside pattern and how does it work?
A: In Cache-Aside, the application first checks the cache for data; on a cache miss, it fetches the data from the database, stores it in the cache, and returns it. On subsequent requests, the data is served directly from the cache until it's evicted or invalidated. It's the most common and flexible caching pattern.

92. Q: What is the difference between Read-Through and Write-Through caching?
A: In Read-Through caching, the cache itself is responsible for loading data from the database on a miss (transparent to the application). In Write-Through caching, writes go to the cache first, and the cache synchronously writes the data to the database before confirming success, keeping the cache and database always in sync.

93. Q: What is Write-Behind (write-back) caching and what risk does it introduce?
A: In Write-Behind caching, writes are made to the cache immediately and asynchronously flushed to the database later, improving write latency. The risk is data loss - if the cache crashes before the write is persisted to the database, that data is gone.

94. Q: How do you decide which caching strategy to use for a given workload?
A: For read-heavy workloads with tolerance for slightly stale data, Cache-Aside or Read-Through works well. For workloads needing strong consistency between cache and database on writes, Write-Through is safer. For write-heavy workloads where write latency matters more than durability risk, Write-Behind can help, but it needs careful handling of failure scenarios.

95. Q: What are common cache eviction policies (LRU, LFU, FIFO)?
A: LRU (Least Recently Used) evicts the item that hasn't been accessed for the longest time. LFU (Least Frequently Used) evicts the item accessed the fewest number of times. FIFO (First In First Out) evicts the oldest item regardless of access pattern. LRU is the most commonly used because it tends to reflect real-world access patterns well.

96. Q: What is a CDN and how does it reduce latency for end users?
A: A CDN (Content Delivery Network) is a network of geographically distributed servers that cache and serve content close to end users. It reduces latency by serving requests from a nearby edge location instead of a potentially distant origin server, and also reduces load on the origin server.

97. Q: What is a distributed cache and how is it different from a local in-memory cache?
A: A distributed cache (like Redis or Memcached cluster) is a shared cache accessible across multiple application servers, keeping data consistent regardless of which server handles a request. A local in-memory cache lives only within a single server's process, which is faster to access but leads to inconsistent data across servers and is lost when that instance restarts.

98. Q: What is cache invalidation and why is it considered a hard problem?
A: Cache invalidation is the process of removing or updating stale data in the cache when the underlying source data changes. It's hard because you need to balance freshness against performance - invalidating too aggressively defeats the purpose of caching, while invalidating too rarely serves stale data, and coordinating invalidation across distributed caches adds further complexity.

99. Q: What is a cache stampede and how can it be prevented?
A: A cache stampede happens when a popular cached item expires and many concurrent requests simultaneously try to recompute/refetch it, overwhelming the backend. It can be prevented using techniques like locking (only one request recomputes while others wait), staggered expiration times, or serving stale data while asynchronously refreshing it in the background.

100. Q: What is cache warming and when would you use it?
A: Cache warming is proactively loading data into the cache before it's requested, rather than waiting for the first request to trigger a cache miss. It's used before predictable high-traffic events (like a big sale) or right after a cache restart/deployment, to avoid a wave of cold cache misses hitting the database at once.

101. Q: What is the difference between Redis and Memcached?
A: Redis supports rich data structures (lists, sets, sorted sets, hashes), persistence to disk, replication, and pub/sub, making it more versatile. Memcached is simpler, purely in-memory, and optimized for straightforward key-value caching with multi-threaded performance. Redis is generally preferred when you need more than plain caching.

102. Q: How do you decide what TTL (time-to-live) to set for a cached value?
A: TTL depends on how often the underlying data changes and how tolerant the application is to staleness - frequently changing data (like stock prices) needs a short TTL, while rarely changing data (like a country list) can have a long TTL. You also balance memory usage against cache hit rate when choosing TTL values.

103. Q: What is the difference between browser caching and server-side caching?
A: Browser caching stores static assets (images, CSS, JS) directly on the user's device based on HTTP cache headers, avoiding network requests entirely on repeat visits. Server-side caching stores data on the server or in a shared caching layer, reducing load on the backend/database but still requiring a network round trip from the client.

104. Q: What is a negative cache and when is it useful?
A: A negative cache stores the fact that a lookup returned "not found" or an error, so repeated requests for that same missing item don't keep hitting the backend unnecessarily. It's useful for protecting against repeated lookups for non-existent data, though it needs a short TTL to avoid masking data that becomes valid later.

105. Q: How would you cache a frequently-changing leaderboard efficiently?
A: Use an in-memory sorted data structure like Redis's Sorted Set, which supports efficient ranked insertion, updates, and range queries (like "get top 10"). Update scores incrementally in the cache rather than recomputing the whole leaderboard, and periodically persist snapshots to the database for durability.

106. Q: What is the 'thundering herd' problem and how is it related to cache stampede?
A: The thundering herd problem is a general term for many processes/threads waking up and competing for a resource at the same time, often causing contention or overload. Cache stampede is a specific instance of this problem, where many requests simultaneously try to regenerate the same expired cache entry.


=== SECTION 7: DATABASES ===

107. Q: What are the main types of databases and how do you choose between them?
A: Main types include relational (SQL), document, key-value, wide-column, graph, time-series, and search/vector databases. You choose based on your data's structure, query patterns, consistency needs, and scale requirements - e.g., relational for structured data with complex relationships and transactions, key-value for simple fast lookups, graph for highly connected data.

108. Q: What is the difference between SQL and NoSQL databases?
A: SQL (relational) databases use structured schemas, tables, and relationships, and typically provide strong ACID guarantees, making them ideal for structured data with complex queries. NoSQL databases use flexible schemas and are designed to scale horizontally more easily, often trading some consistency guarantees for performance and flexibility with unstructured or semi-structured data.

109. Q: What does ACID stand for and why does it matter for transactions?
A: ACID stands for Atomicity (all-or-nothing execution), Consistency (data remains valid according to defined rules), Isolation (concurrent transactions don't interfere with each other), and Durability (committed data survives crashes). It matters because it guarantees transactions behave predictably and safely, which is critical for things like financial systems.

110. Q: What are relational databases best suited for?
A: Relational databases are best suited for structured data with clear relationships, where data integrity and complex queries/joins across tables matter - such as financial systems, inventory management, and order processing systems that need strong ACID guarantees.

111. Q: What is a document database and when would you choose one (e.g. MongoDB)?
A: A document database stores data as flexible, JSON-like documents rather than rigid rows/columns. You'd choose one when your data structure varies between records, evolves frequently, or naturally nests (like a user profile with varying fields), and you don't need complex multi-table joins.

112. Q: What is a key-value store and what are its typical use cases (e.g. Redis, DynamoDB)?
A: A key-value store maps unique keys to values with extremely fast, simple lookups. Typical use cases include caching, session storage, and shopping carts - anywhere you need very fast reads/writes by a known key and don't need complex queries across the dataset.

113. Q: What is a wide-column database and how does it differ from a relational table (e.g. Cassandra)?
A: A wide-column database organizes data into rows with dynamic, flexible sets of columns that can differ between rows, unlike a relational table where every row has the exact same fixed columns. It's optimized for very large-scale, write-heavy workloads distributed across many nodes, like time-series or IoT data.

114. Q: What is a graph database and when is it the right choice (e.g. Neo4j)?
A: A graph database stores data as nodes and edges, optimized for traversing relationships. It's the right choice when relationships between entities are as important as the entities themselves, such as social networks, recommendation engines, or fraud detection where you need to efficiently query connections.

115. Q: What is a time-series database and what workloads is it optimized for?
A: A time-series database is optimized for storing and querying data points indexed by time, such as metrics, sensor readings, or stock prices. It's optimized for high write throughput of timestamped data and efficient range queries/aggregations over time windows.

116. Q: What is a full-text search engine and why can't a regular database replace it (e.g. Elasticsearch)?
A: A full-text search engine (like Elasticsearch) is built specifically for fast, relevance-ranked searching across large volumes of text, using inverted indexes. Regular databases can do basic text matching but aren't optimized for ranking relevance, fuzzy matching, or searching across huge unstructured text efficiently.

117. Q: What is a vector database and why has it become important for AI applications?
A: A vector database stores high-dimensional numerical vectors (embeddings) and efficiently finds the "nearest" vectors to a given query vector. It's become important for AI applications like semantic search and recommendation systems, where similarity between pieces of content (text, images) needs to be measured mathematically rather than through exact matching.

118. Q: What is a B-Tree/B+ Tree and why do relational databases use them for indexing?
A: A B-Tree/B+ Tree is a self-balancing tree structure that keeps data sorted and allows searches, insertions, and deletions in logarithmic time. Relational databases use them for indexes because they're efficient for both point lookups and range queries, and they minimize disk I/O by keeping the tree shallow and wide.

119. Q: What is an LSM Tree and why do many NoSQL databases use it for writes?
A: An LSM (Log-Structured Merge) Tree buffers writes in memory and periodically flushes them to disk in sorted, immutable files, merging them in the background. Many NoSQL databases use it because it turns random writes into fast sequential writes, which is much more efficient for write-heavy workloads than updating data in place.

120. Q: How do databases guarantee durability after a transaction is committed (e.g. write-ahead logs)?
A: Databases typically use a Write-Ahead Log (WAL), where changes are first written to a durable, append-only log before being applied to the actual data files. If the database crashes, it can replay the log on restart to recover any committed changes that hadn't yet been fully written to disk.

121. Q: What is the difference between a primary key and a foreign key?
A: A primary key uniquely identifies each record in a table and cannot be null or duplicated. A foreign key is a field in one table that references the primary key of another table, establishing and enforcing a relationship between the two tables.

122. Q: What is database normalization and why is it done?
A: Normalization is the process of organizing data into multiple related tables to reduce redundancy and improve data integrity, following a series of "normal forms." It's done to avoid data anomalies (like inconsistent duplicate data) and reduce storage waste, though it can require more joins at query time.

123. Q: What is a database transaction and why is isolation level important?
A: A transaction is a group of one or more operations that execute as a single atomic unit - either all succeed or all fail. The isolation level determines how much concurrent transactions can see of each other's uncommitted changes, and it matters because stricter isolation prevents bugs like dirty reads but can reduce concurrency/performance.

124. Q: What is optimistic locking versus pessimistic locking?
A: Optimistic locking assumes conflicts are rare - it lets transactions proceed without locking data upfront, then checks for conflicts (e.g., via a version number) before committing, retrying if a conflict is found. Pessimistic locking locks the data upfront to prevent other transactions from touching it until the lock is released, which avoids conflicts but reduces concurrency.

125. Q: What is a deadlock in a database and how can it be avoided?
A: A deadlock occurs when two or more transactions are each waiting for a lock held by the other, so none of them can proceed. It can be avoided by always acquiring locks in a consistent order, keeping transactions short, using timeouts, or relying on the database's automatic deadlock detection to kill one of the transactions.

126. Q: What is the difference between a clustered and a non-clustered index?
A: A clustered index determines the physical order in which data is stored on disk, so a table can have only one. A non-clustered index is a separate structure that stores pointers back to the actual data rows, so a table can have multiple non-clustered indexes, each optimized for different query patterns.

127. Q: What is database vacuuming/compaction and why do LSM-based stores need it?
A: Vacuuming/compaction is the process of reclaiming space from deleted or outdated data and merging smaller data files into larger, more efficient ones. LSM-based stores need it because writes/updates/deletes are appended rather than modified in place, so old, obsolete versions of data accumulate over time and must be periodically cleaned up (compacted).

128. Q: What is the difference between OLTP and OLAP workloads?
A: OLTP (Online Transaction Processing) handles many small, fast read/write operations for day-to-day application use, like processing an order. OLAP (Online Analytical Processing) handles complex queries over large volumes of historical data for analytics and reporting, like calculating quarterly sales trends. They typically use differently optimized database systems.

129. Q: What is a composite index and when would you create one?
A: A composite index is an index built on multiple columns together rather than just one. You'd create one when queries frequently filter or sort by a combination of columns together (e.g., "last_name, first_name"), since a composite index can serve that query far more efficiently than separate single-column indexes.

130. Q: Why do NoSQL databases often relax ACID guarantees in favor of BASE?
A: NoSQL databases often relax ACID in favor of BASE (Basically Available, Soft state, Eventual consistency) because strict ACID guarantees are hard to maintain efficiently across many distributed nodes. BASE trades strict consistency for higher availability and better horizontal scalability, which suits many large-scale, distributed use cases.


=== SECTION 8: DATABASE SCALING TECHNIQUES ===

131. Q: What is database indexing and how does it speed up reads?
A: An index is a separate data structure (usually a B-Tree) that allows the database to quickly locate rows matching a query condition, without scanning the entire table. It speeds up reads by turning what would be an O(n) full table scan into a much faster O(log n) lookup.

132. Q: What is vertical partitioning of a database table?
A: Vertical partitioning splits a table's columns across multiple tables or storage locations, typically separating frequently accessed columns from rarely accessed ones. This can improve performance by keeping "hot" data compact and cache-friendly while offloading large, rarely used columns (like a big text blob) elsewhere.

133. Q: What are common query optimization techniques for slow queries?
A: Common techniques include adding appropriate indexes, avoiding SELECT * (fetching only needed columns), analyzing query execution plans to spot inefficiencies, avoiding N+1 query patterns, denormalizing where appropriate, and caching results of expensive repeated queries.

134. Q: What are read replicas and how do they help scale a read-heavy system?
A: Read replicas are copies of the primary database that are kept in sync (usually via replication) and used to serve read queries. They help scale read-heavy systems by distributing read traffic across multiple servers instead of overloading a single primary database, while writes still go to the primary.

135. Q: What is denormalization and when is it worth the trade-off?
A: Denormalization deliberately introduces redundant data (e.g., duplicating a field across tables) to avoid expensive joins at read time. It's worth the trade-off in read-heavy systems where query performance matters more than storage efficiency or having a single source of truth for updates.

136. Q: What is a materialized view and how is it different from a regular view?
A: A regular view is essentially a saved query that's recomputed every time it's accessed. A materialized view stores the precomputed results physically, so queries against it are much faster, at the cost of needing periodic refreshes to stay up to date with the underlying data.

137. Q: What is connection pooling and why is it necessary?
A: Connection pooling maintains a reusable pool of database connections instead of opening and closing a new connection for every request. It's necessary because establishing a database connection is relatively expensive, and without pooling, high traffic would quickly exhaust database resources or add significant latency.

138. Q: What is database sharding and what are common sharding strategies?
A: Sharding splits a database's data across multiple independent database instances (shards), each holding a subset of the data. Common strategies include range-based sharding (splitting by value ranges), hash-based sharding (splitting by a hash of a key), and directory-based sharding (using a lookup table to map keys to shards).

139. Q: What is the difference between sharding and partitioning?
A: Partitioning is a broader term for splitting data into smaller chunks, which can happen within a single database instance (e.g., partitioning a table by date). Sharding specifically refers to partitioning data across multiple separate database instances/servers, often to scale beyond what a single machine can handle.

140. Q: What is data compression and how does it help database scaling?
A: Data compression reduces the physical size of stored data using encoding algorithms. It helps scaling by reducing disk space usage, lowering I/O since less data needs to be read from disk, and reducing network transfer time between nodes, though it adds some CPU overhead for compress/decompress operations.

141. Q: What is replication lag and why does it happen with read replicas?
A: Replication lag is the delay between when a write happens on the primary database and when that change is reflected on a read replica. It happens because replication typically occurs asynchronously over a network, and the replica has to receive and apply the change after the primary already committed it.

142. Q: What is a hot partition/hot shard and how can it be avoided?
A: A hot partition/shard is one that receives disproportionately more traffic than others, becoming a bottleneck even though the overall system is "distributed." It can be avoided by choosing a good shard key that distributes load evenly (e.g., hashing rather than sequential IDs) and monitoring for skewed access patterns.

143. Q: What is the difference between range-based sharding and hash-based sharding?
A: Range-based sharding assigns contiguous ranges of a key (e.g., user IDs 1-1000, 1001-2000) to each shard, which is simple and supports efficient range queries but risks hot spots if traffic isn't evenly distributed across ranges. Hash-based sharding applies a hash function to the key to decide the shard, giving a more even distribution but making range queries across shards harder.

144. Q: How do you handle a schema change (migration) on a sharded database with minimal downtime?
A: Roll out the schema change incrementally, shard by shard, rather than all at once, and use backward-compatible changes (e.g., add new columns instead of renaming existing ones immediately) so old and new application code can coexist during the rollout. Automated migration tools and feature flags help coordinate this safely.

145. Q: What is a resharding operation and why is it operationally difficult?
A: Resharding is redistributing data across a different (usually larger) number of shards, typically because the current sharding scheme has become unbalanced or insufficient. It's operationally difficult because it involves moving large amounts of live data without downtime, keeping data consistent during the migration, and updating all routing logic to point to the new shard layout.


=== SECTION 9: STORAGE SYSTEMS ===

146. Q: What is the difference between block storage, file storage, and object storage?
A: Block storage splits data into fixed-size blocks accessed directly by the OS, offering high performance and flexibility, often used for databases (e.g., AWS EBS). File storage organizes data in a hierarchical folder/file structure accessed over a network (e.g., NFS). Object storage stores data as immutable objects with metadata, accessed via APIs, and is ideal for large volumes of unstructured data like images and backups (e.g., AWS S3).

147. Q: What is object storage and why is it well suited for unstructured data (e.g. S3)?
A: Object storage stores data as self-contained objects (data + metadata + a unique ID) in a flat namespace, rather than a folder hierarchy. It's well suited for unstructured data because it scales massively, is durable and cost-effective, and each object can be accessed independently via a simple API without needing filesystem-style navigation.

148. Q: What is a distributed file system and how does it ensure fault tolerance (e.g. HDFS)?
A: A distributed file system stores files across many machines while presenting them as a unified filesystem. It ensures fault tolerance by replicating each block of data across multiple nodes, so if one node fails, the data remains available from the other replicas.

149. Q: What is erasure coding and how is it different from simple replication for durability?
A: Erasure coding splits data into fragments, adds redundant parity fragments, and distributes them across nodes, allowing the original data to be reconstructed even if some fragments are lost - achieving durability with less storage overhead than full replication. Simple replication just stores multiple full copies of the data, which is simpler but uses significantly more storage for the same fault tolerance.

150. Q: What is the difference between a NAS and a SAN?
A: A NAS (Network Attached Storage) provides file-level storage accessed over a standard network using protocols like NFS or SMB, appearing as shared folders. A SAN (Storage Area Network) provides block-level storage over a dedicated high-speed network, appearing to servers as if it were a local disk, and is typically used for performance-critical applications like databases.

151. Q: How does object storage handle metadata compared to a traditional file system?
A: Object storage attaches rich, customizable metadata directly to each object (like tags, content type, and custom key-value pairs), which can be queried independently of the data itself. Traditional file systems have more limited, fixed metadata (like file name, size, and modification date) tied to the hierarchical folder structure.


=== SECTION 10: TRADEOFFS ===

152. Q: What is the trade-off between vertical scaling and horizontal scaling?
A: Vertical scaling is simpler (no application changes needed) but has a hard ceiling based on the biggest machine available and creates a single point of failure. Horizontal scaling has virtually no upper limit and improves fault tolerance, but requires the application to be designed to run across multiple machines (e.g., stateless services, distributed data).

153. Q: What is the difference between concurrency and parallelism?
A: Concurrency is about managing multiple tasks that make progress during overlapping time periods, potentially on a single core by interleaving execution. Parallelism is about literally executing multiple tasks at the exact same time, which requires multiple cores/processors. A system can be concurrent without being parallel.

154. Q: What is the difference between push-based and pull-based architectures?
A: In a push-based architecture, the source actively sends data to consumers as soon as it's available (like webhooks or pub/sub). In a pull-based architecture, consumers periodically request data from the source when they're ready (like polling an API). Push reduces latency and wasted requests, but pull gives the consumer more control over pacing.

155. Q: What is the trade-off between stateful and stateless service design?
A: Stateless services don't store client-specific data between requests, making them trivially easy to scale horizontally and simple to reason about, but sometimes require extra round trips to fetch context. Stateful services can be more efficient for certain workloads (keeping context in memory) but are harder to scale and fail over, since a specific server "owns" the state.

156. Q: How do long polling and WebSockets compare in terms of overhead and complexity?
A: Long polling reuses standard HTTP infrastructure and is simpler to implement, but has more overhead since each "cycle" involves reopening a connection and going through HTTP request/response overhead repeatedly. WebSockets have higher initial setup complexity but much lower ongoing overhead once established, since a single persistent connection handles many messages in both directions.

157. Q: What is the trade-off between strong consistency and eventual consistency?
A: Strong consistency guarantees every read reflects the latest write, which is easier to reason about but typically requires more coordination between nodes, increasing latency and reducing availability during network issues. Eventual consistency allows higher availability and lower latency by relaxing that guarantee, but the application has to tolerate temporarily stale reads.

158. Q: What is the trade-off between normalization and denormalization?
A: Normalization reduces data redundancy and keeps a single source of truth, making writes/updates simpler and safer, but often requires more joins, which can slow down reads. Denormalization speeds up reads by duplicating data, at the cost of more complex writes (needing to update multiple copies) and increased storage.

159. Q: What is the trade-off between using a cache versus scaling the database directly?
A: Caching is usually cheaper and faster to implement, and dramatically reduces load on the database for repeated reads, but introduces the complexity of cache invalidation and potential staleness. Scaling the database directly (e.g., adding read replicas or sharding) avoids staleness concerns but is more complex and costly to set up and maintain.


=== SECTION 11: ARCHITECTURAL PATTERNS ===

160. Q: What is the client-server architecture model?
A: In the client-server model, clients (like browsers or mobile apps) send requests to a central server, which processes them and returns responses. It's the foundational model of most web applications, providing a clear separation between the user-facing side and the backend logic/data.

161. Q: What are the pros and cons of a monolithic architecture?
A: Pros: simpler to develop, test, deploy, and reason about initially, since everything is in one codebase and deployment unit. Cons: harder to scale individual components independently, a bug in one part can bring down the whole application, and it becomes harder to maintain as the codebase and team grow.

162. Q: What are the pros and cons of a microservices architecture?
A: Pros: services can be developed, deployed, and scaled independently, using different technologies as needed, and failures can be isolated to a single service. Cons: significantly more operational complexity (networking, service discovery, distributed debugging), and it introduces challenges like data consistency across services that don't exist in a monolith.

163. Q: What is serverless architecture and when does it make sense?
A: Serverless architecture lets you run code (functions) without managing servers - the cloud provider automatically handles provisioning and scaling, and you're billed per execution. It makes sense for event-driven, sporadic, or unpredictable workloads where you don't want to pay for idle server time, though it's less ideal for long-running or highly latency-sensitive processes due to cold starts.

164. Q: What is event-driven architecture and how does it decouple services?
A: In event-driven architecture, services communicate by publishing and reacting to events rather than calling each other directly. This decouples services because the publisher doesn't need to know who's listening or what they'll do - new subscribers can be added without modifying the publisher.

165. Q: What is peer-to-peer (P2P) architecture and where is it used?
A: In P2P architecture, nodes (peers) communicate directly with each other without relying on a central server, each acting as both client and server. It's used in file-sharing systems (like BitTorrent), blockchain networks, and some real-time communication systems.

166. Q: What is hexagonal architecture and what problem does it solve?
A: Hexagonal architecture (Ports and Adapters) structures an application so the core business logic is isolated from external concerns (databases, APIs, UI) through defined interfaces (ports) and implementations (adapters). It solves the problem of tightly coupling business logic to specific frameworks or infrastructure, making the system easier to test and swap external dependencies.

167. Q: What is CQRS (Command Query Responsibility Segregation) and why would you use it?
A: CQRS separates the model used for writing data (commands) from the model used for reading data (queries), often using entirely different data stores optimized for each. You'd use it when read and write workloads have very different performance or scaling needs, allowing each side to be optimized and scaled independently.

168. Q: What is event sourcing and how is it different from storing just the current state?
A: Event sourcing stores every change to application state as an immutable sequence of events, and the current state is derived by replaying those events, rather than storing just the latest snapshot. This provides a complete audit trail and the ability to reconstruct past states, at the cost of added complexity in querying and managing the growing event log.

169. Q: When would you choose serverless over a traditional containerized microservice?
A: Choose serverless for lightweight, infrequent, or highly variable workloads (like processing an occasional file upload) where you don't want to manage infrastructure or pay for idle capacity. Choose a traditional containerized microservice for workloads with steady traffic, long-running processes, or strict latency requirements where cold starts would be a problem.

170. Q: What is the trade-off of choosing microservices too early in a startup's life?
A: Microservices add significant operational overhead (networking, deployment pipelines, monitoring, data consistency across services) that can slow down a small team more than it helps, especially before the product or team has grown large enough to need that independent scalability. Many successful companies start with a monolith and split into microservices only once specific parts of the system clearly need to scale or be owned independently.

171. Q: What is a shared-nothing architecture and why is it favored for scalability?
A: In a shared-nothing architecture, each node is independent and self-sufficient, with no shared memory or storage between nodes - every node has its own CPU, memory, and disk. It's favored for scalability because it eliminates contention/bottlenecks from shared resources, allowing nodes to be added almost linearly to increase capacity.

172. Q: What is the difference between orchestration and choreography in service communication?
A: In orchestration, a central controller explicitly directs the interaction between services, telling each one what to do and when. In choreography, there's no central controller - each service listens for events and reacts independently, publishing its own events for others to react to, resulting in a more decentralized flow.

173. Q: What is a modular monolith and how does it bridge monolith and microservices trade-offs?
A: A modular monolith is a single deployable application internally organized into well-defined, loosely coupled modules with clear boundaries, similar to how microservices are separated, but without the network/deployment overhead of actually splitting them into separate services. It bridges the trade-offs by giving teams the code organization benefits of microservices while keeping the operational simplicity of a monolith, and can be split into real microservices later if needed.


=== SECTION 12: MICROSERVICES PATTERNS ===

174. Q: What is service discovery and why is it needed in a microservices architecture?
A: Service discovery is a mechanism that allows services to find the network location (IP/port) of other services dynamically, since instances can be added, removed, or rescheduled frequently. It's needed because hardcoding service addresses doesn't work in an environment where instances scale up/down and get replaced constantly.

175. Q: What is the API Gateway pattern in a microservices system?
A: The API Gateway pattern puts a single entry point in front of all microservices, handling routing, authentication, and cross-cutting concerns, so clients interact with one unified interface instead of knowing about every individual service's address and API.

176. Q: What is the Backend-for-Frontend (BFF) pattern and why is it used?
A: BFF creates a separate backend layer tailored specifically to the needs of each client type (e.g., one BFF for mobile, one for web), rather than one generic API serving all clients. It's used because different clients often need different data shapes or aggregations, and a single shared API can become a bloated compromise for everyone.

177. Q: What is the Sidecar pattern and how is it used in a service mesh?
A: The Sidecar pattern attaches a helper process (like a proxy) alongside each service instance to handle cross-cutting concerns (networking, security, observability) without modifying the service's own code. In a service mesh, sidecars intercept all inbound/outbound traffic for a service, providing consistent policy enforcement and telemetry across every service in the mesh.

178. Q: What is the Circuit Breaker pattern and how does it prevent cascading failures?
A: The Circuit Breaker pattern monitors calls to a downstream service and "trips" to stop sending requests once failures exceed a threshold, failing fast instead of waiting on timeouts. This prevents cascading failures by stopping a struggling downstream service from being overwhelmed further and stopping the calling service from getting bogged down waiting on doomed requests.

179. Q: What is the Bulkhead pattern and how does it isolate failures?
A: The Bulkhead pattern partitions resources (like thread pools or connections) so that failures or slowness in one part of the system can't consume all available resources and starve unrelated parts of the system. It's named after ship bulkheads, which prevent a single hull breach from flooding the entire vessel.

180. Q: What is the Strangler Fig pattern and when would you use it for migration?
A: The Strangler Fig pattern gradually replaces parts of a legacy system with new services, routing an increasing share of traffic to the new implementation over time until the old system can be fully retired. It's used to migrate a system incrementally and safely, rather than attempting a risky "big bang" rewrite.

181. Q: What is a Service Mesh and what problems does it solve for microservices?
A: A service mesh is a dedicated infrastructure layer (usually via sidecar proxies) that manages service-to-service communication, handling things like load balancing, retries, encryption, and observability. It solves the problem of having to implement these cross-cutting networking concerns separately in every service's code.

182. Q: What is the difference between client-side and server-side service discovery?
A: In client-side discovery, the calling service queries a registry directly and decides which instance to call. In server-side discovery, the client calls a load balancer/router, which queries the registry and forwards the request on the client's behalf, keeping the discovery logic out of the client entirely.

183. Q: How does the Circuit Breaker pattern's half-open state work?
A: After tripping open and waiting a cooldown period, the circuit breaker enters a half-open state where it allows a limited number of test requests through. If those succeed, the breaker closes and resumes normal traffic; if they fail, it goes back to open and waits again before retrying.

184. Q: What is a retry policy with exponential backoff and why is jitter added to it?
A: Exponential backoff increases the wait time between retries exponentially (e.g., 1s, 2s, 4s, 8s) instead of retrying immediately, giving a struggling service time to recover. Jitter adds randomness to that wait time so that many clients retrying simultaneously don't all retry at the exact same moment and cause another spike of load (a "retry storm").


=== SECTION 13: DISTRIBUTED SYSTEM FUNDAMENTALS ===

185. Q: What are the main challenges introduced by distributing a system across multiple nodes?
A: Key challenges include network unreliability (messages can be delayed, lost, or duplicated), maintaining consistency across nodes, handling partial failures (some nodes up, some down), clock synchronization, and the added operational complexity of coordinating and debugging many independent components.

186. Q: What is a network partition and how should a system handle one?
A: A network partition occurs when a network failure splits nodes into groups that can't communicate with each other, even though each group is individually still running. A system should have a defined strategy for this scenario per the CAP theorem - either continue serving requests with reduced consistency (favoring availability) or refuse some requests to maintain consistency.

187. Q: What is the split-brain problem in distributed systems?
A: Split-brain occurs when a network partition causes two (or more) groups of nodes to each believe they are the sole authoritative leader/primary, leading to conflicting writes and data divergence. It's typically prevented using quorum-based decision making, so only a group with a majority of nodes can act as the leader.

188. Q: What are heartbeats used for in distributed systems?
A: Heartbeats are periodic "I'm alive" signals sent between nodes to detect failures quickly. If a node stops sending heartbeats within an expected time window, other nodes assume it has failed and can trigger failover or remove it from the pool of healthy nodes.

189. Q: What are common strategies for handling failures in distributed systems?
A: Common strategies include retries with backoff, timeouts, circuit breakers, redundancy/replication, failover to a healthy replica, and graceful degradation. The general philosophy is to design for failure as the expected case rather than an edge case.

190. Q: What is the clock synchronization problem across distributed nodes?
A: Since each machine has its own physical clock which can drift slightly over time, different nodes may disagree on the exact current time. This makes it unreliable to use physical timestamps alone to determine the true order of events across a distributed system, which is why logical clocks are often used instead.

191. Q: What are logical clocks and why are they used instead of physical clocks?
A: Logical clocks (like Lamport timestamps or vector clocks) track the relative ordering of events based on cause and effect rather than actual wall-clock time. They're used instead of physical clocks because they don't depend on perfectly synchronized machine clocks, and they correctly capture causality even when physical clocks drift or are out of sync.

192. Q: What are Lamport timestamps and what ordering guarantee do they provide?
A: Lamport timestamps assign a counter to each event, incrementing it locally and updating it based on received messages, so that if event A causally influenced event B, A's timestamp will always be smaller than B's. They provide a "happens-before" partial ordering, though they can't distinguish concurrent (unrelated) events from each other.

193. Q: What is a consensus algorithm and why is consensus hard in distributed systems?
A: A consensus algorithm allows multiple distributed nodes to agree on a single value or decision even in the presence of failures or network issues. It's hard because nodes can fail, messages can be delayed or lost, and the algorithm must still guarantee correctness (all correct nodes eventually agree) despite this unreliability.

194. Q: What is leader election and why is it needed in distributed systems?
A: Leader election is the process by which a group of distributed nodes selects one node to act as the coordinator/leader for a period of time. It's needed to avoid conflicts that arise when multiple nodes try to make the same decision independently (e.g., only one node should be the primary database at a time).

195. Q: What is a distributed lock and what problem does it solve?
A: A distributed lock ensures that only one process across multiple machines can access a shared resource or perform a critical operation at a time. It solves the same mutual-exclusion problem as a regular lock, but across a network of independent processes rather than within a single machine's memory.

196. Q: What is the Gossip Protocol and how is it used to spread information in a cluster?
A: The Gossip Protocol spreads information through a cluster by having each node periodically share what it knows with a few randomly chosen peers, similar to how rumors spread among people. Over time this propagates updates (like cluster membership or health status) to the entire cluster without needing a central coordinator.

197. Q: What is a vector clock used for in distinguishing concurrent events?
A: A vector clock tracks a counter per node (not just one global counter like Lamport timestamps), allowing the system to detect whether two events are causally related or truly concurrent (independent). This is useful for conflict detection in distributed/replicated systems, like resolving conflicting writes.

198. Q: What is the Raft consensus algorithm used for at a high level?
A: Raft is a consensus algorithm used to keep a cluster of nodes in agreement on a replicated log of operations, ensuring all nodes apply the same sequence of changes even if some nodes fail. It works by electing a leader that handles all writes and replicates them to followers, and is designed to be easier to understand than alternatives like Paxos.

199. Q: What is a quorum and why is it used for reads/writes in distributed systems?
A: A quorum is the minimum number of nodes that must agree/participate for a read or write to be considered successful (often more than half the nodes). It's used to guarantee consistency - by requiring overlapping quorums for reads and writes, the system ensures a read will always see the most recent write, even with some nodes unavailable.

200. Q: What is idempotency's role in safely retrying failed requests in a distributed system?
A: Since network failures make it impossible to always know whether a request actually succeeded on the other end, clients often need to retry. Idempotency ensures that retrying a request that already succeeded doesn't cause unintended side effects (like double-processing a payment), making retries safe by design.


=== SECTION 14: DISTRIBUTED TRANSACTIONS ===

201. Q: Why are distributed transactions harder than single-database transactions?
A: A single database can enforce ACID guarantees internally using locks and a single write-ahead log. Distributed transactions span multiple independent systems/databases over an unreliable network, so coordinating atomicity (all-or-nothing) across them requires complex protocols and introduces risks like partial failures, network delays, and reduced availability.

202. Q: What is the Two-Phase Commit (2PC) protocol and what is its main drawback?
A: In 2PC, a coordinator first asks all participants to "prepare" (vote yes/no) to commit a transaction, and only if all vote yes does it send a "commit" command to everyone; if any vote no, it tells everyone to abort. Its main drawback is that it's a blocking protocol - if the coordinator crashes after the prepare phase, participants can be left waiting indefinitely, holding locks.

203. Q: What is the Three-Phase Commit (3PC) protocol and how does it improve on 2PC?
A: 3PC adds an extra "pre-commit" phase between prepare and commit, giving participants a way to time out and safely abort or complete the transaction independently if the coordinator fails, reducing the blocking problem in 2PC. However, it's more complex and still doesn't fully solve consistency issues under certain network partition scenarios.

204. Q: What is the Saga pattern and how does it manage distributed transactions?
A: The Saga pattern breaks a distributed transaction into a sequence of local transactions, each with a corresponding compensating action that can undo it if a later step fails. Instead of a single atomic commit across services, the saga either completes all steps successfully or runs compensating actions to roll back the steps that already succeeded.

205. Q: What is the Outbox pattern and what problem does it solve?
A: The Outbox pattern writes an event to an "outbox" table in the same local database transaction as the actual business data change, then a separate process reliably publishes that event to a message broker. It solves the problem of atomically updating a database and publishing an event, which can't otherwise be guaranteed together without this trick (avoiding the "dual write" problem).

206. Q: What is the difference between an orchestrated Saga and a choreographed Saga?
A: In an orchestrated Saga, a central coordinator explicitly tells each service what step to perform next and handles the overall flow. In a choreographed Saga, there's no central coordinator - each service reacts to events published by the previous step and publishes its own event when done, creating a decentralized flow.

207. Q: What is a compensating transaction and why is it needed in the Saga pattern?
A: A compensating transaction is an operation that semantically undoes the effect of a previously completed step (e.g., refunding a payment that was already charged). It's needed because distributed systems can't roll back a true database transaction across services the way a single database can, so each step needs its own explicit "undo" logic.


=== SECTION 15: DATA STRUCTURES FOR SCALE ===

208. Q: What is a Bloom filter and what trade-off does it make (false positives vs. memory)?
A: A Bloom filter is a compact, probabilistic data structure that tells you whether an element is "possibly in the set" or "definitely not in the set," using far less memory than storing the actual set. The trade-off is it can produce false positives (saying an item might be present when it isn't) but never false negatives, in exchange for its huge space savings.

209. Q: What is a Geohash and how is it used in location-based systems?
A: A Geohash encodes a latitude/longitude coordinate into a short alphanumeric string, where nearby locations tend to share similar prefixes. It's used in location-based systems to efficiently index and query for nearby points (like "restaurants near me") using simple string prefix matching instead of complex geometric calculations.

210. Q: What is HyperLogLog and what problem does it solve at scale?
A: HyperLogLog is a probabilistic algorithm used to estimate the number of distinct (unique) elements in a very large dataset using a small, fixed amount of memory. It solves the problem of counting unique visitors or unique values at massive scale, where storing every unique value to count them exactly would require far too much memory.

211. Q: What is a Skip List and where is it used in real systems?
A: A Skip List is a layered linked-list structure that allows fast search, insertion, and deletion (similar to a balanced tree) by using multiple levels of "shortcuts" over a sorted list. It's used in systems like Redis's sorted sets, where it provides efficient ordered operations with simpler implementation than a balanced tree.

212. Q: What is a Merkle Tree and how is it used to verify data consistency?
A: A Merkle Tree is a tree where every leaf node is a hash of a data block, and every non-leaf node is a hash of its children's hashes, up to a single root hash summarizing all the data. It's used to efficiently verify data consistency between replicas - comparing root hashes quickly reveals if any data differs, and you can drill down the tree to find exactly which piece changed.

213. Q: What is a Quad Tree and how is it used for spatial indexing?
A: A Quad Tree recursively divides 2D space into four quadrants, subdividing further wherever data is dense, to efficiently index spatial data. It's used for spatial indexing in applications like maps or games, enabling fast queries like "find all points within this region."

214. Q: What is a Count-Min Sketch used for when exact counts aren't feasible?
A: A Count-Min Sketch is a probabilistic data structure that estimates the frequency of items in a stream using a small, fixed amount of memory, at the cost of occasionally overestimating counts. It's used when you need approximate frequency counts (like "top trending searches") over massive, high-volume data streams where exact counting would be too memory-intensive.

215. Q: Why would a system use a Bloom filter before checking a database, e.g. to avoid an unnecessary lookup?
A: Since a Bloom filter can quickly and cheaply confirm "definitely not present," the system can skip an expensive database lookup entirely for items that don't exist, only querying the database when the Bloom filter says "possibly present." This saves significant load on the database, especially for systems with many lookups for non-existent keys.

216. Q: What is a Trie and how is it used for autocomplete features?
A: A Trie (prefix tree) stores strings character by character in a tree structure, where common prefixes share the same path. It's used for autocomplete because, given a prefix typed by a user, you can quickly traverse to that node and retrieve all words that share it, without scanning the entire dataset.

217. Q: What is an R-Tree and how is it used to index geographic/spatial data?
A: An R-Tree groups nearby spatial objects into bounding boxes arranged hierarchically, similar to a B-Tree but for multi-dimensional data. It's used to efficiently answer spatial queries like "find all objects that overlap this region" without scanning every object.

218. Q: What is the space-time trade-off made by probabilistic data structures like Bloom filters?
A: Probabilistic data structures sacrifice perfect accuracy (allowing a small, tunable error rate) in exchange for dramatically reduced memory usage and faster operations compared to exact data structures. This trade-off is worthwhile at scale, where storing/processing exact data would be prohibitively expensive, and an approximate answer is good enough.


=== SECTION 16: BIG DATA PROCESSING ===

219. Q: What is the difference between batch processing and stream processing?
A: Batch processing processes large volumes of data collected over a period of time, all at once, on a schedule (e.g., a nightly report job). Stream processing processes data continuously as it arrives, in near real time, which is necessary for use cases like live fraud detection or real-time dashboards.

220. Q: What is MapReduce and how does it process large datasets in parallel?
A: MapReduce is a programming model for processing large datasets by splitting the work into a "Map" phase (processing/transforming data in parallel across many nodes) and a "Reduce" phase (aggregating the mapped results into a final output). It processes data in parallel by distributing chunks of data and computation across a cluster of machines.

221. Q: What is an ETL pipeline and what are its three stages?
A: ETL stands for Extract (pulling data from source systems), Transform (cleaning, reshaping, and enriching the data), and Load (writing the processed data into a destination system like a data warehouse). It's the standard pattern for moving and preparing data for analytics.

222. Q: What is the difference between a data lake and a data warehouse?
A: A data lake stores raw data in its native format (structured, semi-structured, or unstructured) at low cost, with schema applied only when the data is read. A data warehouse stores structured, cleaned, and organized data with a predefined schema, optimized for fast analytical queries and reporting.

223. Q: What is a data lakehouse and how does it combine lake and warehouse benefits?
A: A data lakehouse is an architecture that adds warehouse-like features (schema enforcement, ACID transactions, fast querying) directly on top of low-cost data lake storage. It combines the flexibility and low cost of a data lake with the reliability and performance of a data warehouse, avoiding the need to maintain two separate systems.

224. Q: What is Lambda Architecture and why does it combine batch and stream processing?
A: Lambda Architecture runs both a batch layer (for accurate, comprehensive processing of historical data) and a speed/stream layer (for low-latency processing of recent data) in parallel, merging their results at query time. It combines both because batch processing gives accuracy at scale, while stream processing gives freshness/low latency, and together they cover both needs.

225. Q: What is Kappa Architecture and how does it simplify Lambda Architecture?
A: Kappa Architecture simplifies Lambda by using only a single stream processing pipeline for both real-time and historical data (by replaying the stream from the beginning when reprocessing is needed), eliminating the need to maintain two separate codebases for batch and stream processing.

226. Q: What is a streaming engine (e.g. Apache Flink/Spark Streaming) used for?
A: A streaming engine processes continuous, unbounded streams of data in real time or near real time, supporting operations like filtering, aggregating, and joining data as it flows through the system. It's used for use cases like real-time analytics, fraud detection, and live monitoring dashboards.

227. Q: What is windowing in stream processing and why is it needed for aggregations?
A: Windowing groups a continuous stream of events into finite chunks (e.g., "the last 5 minutes" or "every 1000 events") so that aggregate operations like sum, count, or average can be computed. It's needed because a stream is technically infinite, so you can't compute an aggregate over "all data" - you need to define bounded windows to get meaningful, timely results.


=== SECTION 17: DEPLOYMENT PATTERNS ===

228. Q: What is a CI/CD pipeline and why is it important for shipping software reliably?
A: A CI/CD (Continuous Integration/Continuous Deployment) pipeline automates building, testing, and deploying code changes. It's important because it catches bugs early through automated testing, ensures consistent and repeatable deployments, and lets teams ship changes to production quickly and safely rather than relying on risky, infrequent manual releases.

229. Q: What is a rolling deployment and how does it minimize downtime?
A: A rolling deployment gradually replaces old instances of a service with new ones, a few at a time, rather than taking everything down at once. This minimizes downtime because some instances are always available to serve traffic throughout the deployment process.

230. Q: What is blue-green deployment and how does it reduce release risk?
A: Blue-green deployment maintains two identical production environments ("blue" - current, and "green" - new); traffic is switched from blue to green all at once after the new version is verified. It reduces release risk because you can instantly switch traffic back to the old environment if something goes wrong, with minimal downtime either way.

231. Q: What is a canary release and how does it differ from blue-green deployment?
A: A canary release gradually rolls out a new version to a small subset of users/traffic first, monitoring for issues before expanding to everyone. Unlike blue-green (which switches all traffic at once between two full environments), canary releases allow issues to be caught with limited blast radius before a full rollout.

232. Q: What are feature flags and why are they useful for controlled rollouts?
A: Feature flags are toggles that let you turn a feature on or off (or for specific user segments) without deploying new code. They're useful because they decouple deployment from release - you can deploy code with a feature "off," then gradually enable it, and instantly disable it if something goes wrong, without needing a new deployment.

233. Q: What is A/B testing infrastructure used for at a system design level?
A: A/B testing infrastructure routes different segments of users to different variants of a feature (e.g., variant A vs. variant B) and tracks metrics to compare their performance. At a system design level, it needs consistent user bucketing, reliable metric collection, and often integrates with feature flag systems to control which variant a user sees.

234. Q: What is a schema migration and how do you do one without downtime?
A: A schema migration changes a database's structure (like adding a column or table). To do one without downtime, you typically make backward-compatible changes in stages - e.g., add a new column as nullable first, deploy code that writes to both old and new columns, backfill existing data, then switch reads over, and only remove the old column once everything is fully migrated.

235. Q: What is immutable infrastructure and how does it make rollbacks safer?
A: Immutable infrastructure means servers/instances are never modified after deployment - instead, any change results in a brand new instance being created and the old one destroyed. This makes rollbacks safer because reverting is as simple as redeploying the previous known-good image, rather than trying to manually undo changes on a live, potentially inconsistent server.

236. Q: What is the difference between a canary release and A/B testing?
A: A canary release is primarily about safely and gradually verifying a new version's stability/correctness before a full rollout. A/B testing is primarily about comparing the business/user impact of two different variants, often running both versions long-term with real users rather than phasing one out.

237. Q: What is a rollback strategy and why should it be tested before you need it?
A: A rollback strategy defines exactly how to revert to a previous known-good version if a deployment causes problems. It should be tested before you need it because during an actual incident is the worst time to discover your rollback process doesn't actually work or takes too long, so rehearsing it in advance reduces panic and downtime during a real outage.


=== SECTION 18: OBSERVABILITY ===

238. Q: What are the three pillars of observability (logs, metrics, traces)?
A: Logs are detailed, timestamped records of discrete events that help with debugging specific issues. Metrics are numerical measurements aggregated over time (like request rate or error rate) that help spot trends and set alerts. Traces follow a single request's journey across multiple services, helping pinpoint where in a distributed system a slowdown or error occurred.

239. Q: What are logging best practices in a distributed system?
A: Use structured (e.g., JSON) logs rather than free-form text so they're easy to query. Include correlation/request IDs so logs from the same request across services can be tied together. Log at appropriate levels (info, warning, error) and avoid logging sensitive data, and centralize logs so they can be searched across all services in one place.

240. Q: What is log aggregation and why is it needed across many services?
A: Log aggregation collects logs from many different services/instances into a centralized system where they can be searched, filtered, and analyzed together. It's needed because in a distributed system, a single user request might touch dozens of services, and debugging would be nearly impossible if you had to manually check logs on each individual machine.

241. Q: What are correlation IDs and how do they help debug distributed requests?
A: A correlation ID is a unique identifier generated for a request that's passed along to every downstream service it touches. It helps debugging because you can search for that single ID across all services' logs and traces to reconstruct the full journey and timing of that one request, even across many independent systems.

242. Q: What is distributed tracing and how does it help track a request across services?
A: Distributed tracing records timing and metadata for each step (span) a request takes as it flows through multiple services, then stitches those spans together into a single trace. It helps identify exactly which service or step is causing latency or errors in a complex, multi-service request path.

243. Q: What is the difference between monitoring and alerting?
A: Monitoring is the ongoing collection and visualization of system metrics and health data (dashboards you can look at). Alerting is the automated notification system that proactively tells engineers when something crosses a defined threshold or looks abnormal, so problems can be caught even when no one is actively watching a dashboard.

244. Q: What metrics would you track to know if a service is healthy (the four golden signals)?
A: The four golden signals are Latency (how long requests take), Traffic (how much demand the service is receiving), Errors (rate of failed requests), and Saturation (how "full"/close to capacity the service's resources are, like CPU or memory). Together they give a solid baseline view of a service's health.

245. Q: What is a runbook and why is it useful during an incident?
A: A runbook is a documented, step-by-step guide for diagnosing and resolving specific types of incidents or operational tasks. It's useful during an incident because it reduces reliance on tribal knowledge or a single expert, letting any on-call engineer follow a proven process quickly under pressure.

246. Q: What is structured logging and why is it preferred over plain text logs?
A: Structured logging outputs logs in a consistent, machine-parseable format (like JSON) with clearly labeled fields, rather than free-form sentences. It's preferred because it makes logs far easier to search, filter, and analyze programmatically at scale, compared to trying to parse arbitrary text with regex.

247. Q: What is an SLI, SLO, and SLA, and how do they relate to each other?
A: An SLI (Service Level Indicator) is an actual measured metric (like uptime percentage or latency). An SLO (Service Level Objective) is the internal target you aim for on that metric (e.g., 99.9% uptime). An SLA (Service Level Agreement) is an external, often contractual, commitment to customers based on that objective, sometimes with penalties if it's not met.


=== SECTION 19: ADVANCED SECURITY ===

248. Q: What is SSL/TLS and how does it secure data in transit?
A: SSL/TLS is a cryptographic protocol that encrypts data transmitted between a client and server, preventing eavesdropping and tampering. It works by using asymmetric encryption during a handshake to securely exchange a shared symmetric key, which is then used to efficiently encrypt the actual data for the rest of the session.

249. Q: What is encryption at rest and why is it needed in addition to encryption in transit?
A: Encryption at rest encrypts data while it's stored on disk (databases, backups, files), so it can't be read even if someone gains unauthorized physical or file-level access to the storage. It's needed in addition to encryption in transit because encryption in transit only protects data while it's moving over the network - it does nothing to protect stored data from a breach of the storage itself.

250. Q: What is secrets management and why shouldn't credentials be hardcoded?
A: Secrets management refers to securely storing, accessing, and rotating sensitive credentials (API keys, passwords, certificates) using a dedicated tool rather than embedding them directly in code or config files. Credentials shouldn't be hardcoded because source code is often shared, logged, or version-controlled, making hardcoded secrets easy to accidentally leak and hard to rotate when compromised.
